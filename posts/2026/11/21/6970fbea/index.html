从 amend 到 rebase：一次 git 习惯的改变

发表于 2026-11-21 分类于 技术 ， Git 阅读次数： 本文字数： 3.6k 阅读时长 ≈ 6 分钟
记录从 amend 到 rebase 的开发习惯变化，以及在 dev 分支同步 master 的操作方式。

起因是我有个写代码习惯（反复 amend），又想经常同步 master 的代码，结果一路摸到了 rebase。

之前一直不敢用 rebase，现在回想起来，可能是刚入行时某次用 rebase 产生不好的结果，有了心理阴影，加上一直用 merge 养成了习惯，就没再去研究一下 rebase。

1. 我的开发习惯

场景是这样的：

  • master 上有最新代码，我基于它拉了个 dev 分支。
  • 我在 dev 上改某个文件，要改很久，中间不想留一堆零碎提交，希望一直 amend 到同一个提交上。
  • 同时 master 在不断更新，我想时不时把 master 的代码同步过来，而且不打断 amend。

问题就变成：怎么同步 master，才能让我的 HEAD 一直是“我那一个提交”，继续 amend？

2. 最常用的 merge

同步 master 最直觉的做法是在 dev 上 git merge master，就算是没用过 git 的人，看到 merge 就见名知意了。

merge 会产生一个新的合并提交 M，HEAD 变成 M。这时再 git commit --amend，改的是 M，不是我的功能提交 E。我的改动会和合并混在一起，amend 的意义就没了。

补充一点：M 是 D 和 E 的合并，也就是 master 最新提交和当前分支最新提交的合并。

  • M 有两个父提交。第一父提交是我当前所在分支的最新提交，第二父提交是被合并进来的 master 最新提交 D。
  • M 的内容 = 分叉点 B 之后 master 的所有改动（C、D）+ dev 的所有改动，合在一起的结果。
  • C 和 D 并没有被合成一个提交，它们仍然是独立的提交，只是现在从 dev 也能追溯到。

看结构用 git log --graph --oneline，只看 dev 自己的主线用 git log --first-parent。

所以 merge 本身没问题，但它不适合我“要持续 amend 同一个提交”的场景。

3. rebase 是什么

在 dev 分支执行 git rebase master（也叫 rebase dev onto master），Git 会把 dev 上从共同祖先之后的提交依次重放，形成一条以 master 最新提交为起点的 dev 历史。操作完成后，dev 前进到新提交，master 保持不变。

下图中的 E' 就是重放 E 后生成的新提交。

要点：

  • E’ 和 E 内容相同，但 hash 不同，本质是重新创建的提交，旧的 E 没有分支指向它了。
  • 结果是一条直线，没有 merge commit。
  • 效果等价于“我是从 D 才开始开发的”。
  • HEAD 仍然是我那个功能提交 E’，所以可以继续 amend。

这就解决了开头的问题：rebase 同步 master，不会打断 amend。

git 判断“哪些是 dev 独有的”：看 dev 和 master 的共同祖先（这里是 B）。B 之后 dev 上的所有提交，都会被 rebase 处理。

4. dev 上有多笔提交时

如果 dev 上不止一笔，比如 E、F 两笔，git rebase master 会把两笔都按顺序接到 master 最新提交后面。

和单个提交的区别：

  • 冲突可能出现多轮。git 是逐个提交重放的：E 有冲突就停下来，我解决后 git add、git rebase --continue，然后重放 F，F 可能再冲突一次。只有一个提交时，最多解决一轮。
  • amend 改的是最后一笔。rebase 后 HEAD 是 F’，amend 改 F’，不会动 E’。

或者 git rebase -i master，把 F 标成 squash / fixup。

  • squash：合并 F 的改动，并让你编辑合并后的提交说明。
  • fixup：也合并 F 的改动，但直接丢弃 F 的提交说明，保留 E 的说明。

完成后，E 和 F 会变成一个新的提交。squash 和 fixup 都会改写提交历史。

5. 我的日常流程

几个细节：

  • 工作区有未提交的修改时，rebase 会拒绝执行。--autostash 会自动 stash、rebase、再恢复。也可以配置成默认：git config --global rebase.autoStash true。
  • 直接 rebase origin/master。如果用本地 master，要先更新，不然 rebase 的是旧代码。
  • 冲突时：解决文件 → git add → git rebase --continue。想放弃就 git rebase --abort，回到 rebase 之前的状态。
  • 可以开 git config rerere.enabled true，让 git 记住解决过的冲突，相同冲突下次自动应用。

6. 风险和兜底

改写历史

amend 和 rebase 都会生成新提交、丢弃旧提交。如果 dev 已经推送到远程，再推送要强推：

  • --force-with-lease 比 --force 安全：远程分支被别人更新过时会拒绝覆盖。
  • 前提是这个分支只有我自己在用，别人基于它开发会出问题。

改坏了怎么办

  • rebase / merge 进行中：git rebase --abort、git merge --abort。
  • 已经完成但想回退：git reflog 找到操作前的位置，git reset --hard HEAD@{n}。
  • amend 会覆盖上一版，改坏了只能靠 reflog 找回。所以 reflog 值得提前演练一次。

7. 对这个习惯的反思

反复 amend 的代价是覆盖上一版，改坏了只能靠 reflog。还有一条替代路径：

  • 平时正常多次提交，中间状态不丢。
  • 最后用 git rebase -i 或 git reset --soft 压成一个提交。
  • 我们用 GitLab，如果合并 MR 时本来就 squash，那平时多次提交效果一样，也不用为了保持单提交而频繁 rebase。

我坚持 amend，是因为真的需要单提交历史，还是只是习惯？应该是更加方便，毕竟在 pycharm 上只要点击 Amend 即可，也不用更新 message，用上一次的就好了，特别适合频繁修改一个文件、不断查看差异。

最近开始，我已经更习惯用 rebase 而不是 merge 了。稍微难一点的东西，用的多了，理解多了，自然也更加熟练。

速查

想做什么 命令
同步 master 并保持线性 git fetch origin && git rebase --autostash origin/master
同步 master，保留合并记录 git merge origin/master
把修改并进上一个提交 git add -u && git commit --amend --no-edit
rebase 冲突后继续 解决文件 → git add → git rebase --continue
放弃 rebase / merge git rebase --abort / git merge --abort
已推送分支改写历史后推送 git push --force-with-lease
把最近 N 笔压成一笔 git reset --soft HEAD~N && git commit -m "..."
交互式整理提交 git rebase -i master
看提交图 git log --graph --oneline --all
只看当前分支主线 git log --first-parent
找回操作前的状态 git reflog → git reset --hard HEAD@{n}
自动 stash git config --global rebase.autoStash true
记住冲突解决方式 git config rerere.enabled true

选择原则：

  • 只有我自己用的分支：rebase，历史干净。
  • 已推送且别人也在用：merge，不改写历史。
  • 团队有约定（线性历史、squash）：按约定来。
